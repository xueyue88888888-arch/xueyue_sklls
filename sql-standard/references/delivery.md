# 交付契约

每条交给别人用（进报表、进数据集、进跑批）的 SQL，必须带下面三样。

## 一、头注释

```sql
-- 用途：一句话说明这个查询回答什么问题
-- 口径：粒度=一行代表什么；范围=时间/组织/状态过滤；边界=异常与特殊处理
-- 参数：${data_dt} 数据日期，默认最新分区；${org_id} 机构范围，all=全部
-- 输出：列名 + 含义 + 单位（比例/金额/人数要标清）
-- 对账：一行可执行的对账 SQL，或一句可验证的期望
-- 变更：日期 + 谁 + 改了什么
```

缺任何一项，别人接手就要重问一遍口径——这就是返工的来源。

## 二、三段验收

| 段 | 做什么 | 不通过的后果 |
|---|---|---|
| 静态 | `sqlguard check sql/x.sql --profile doris`，P0 必须为 0 | 上线即报错，或静默少数据 |
| 试跑 | `LIMIT 10` 跑通，看空值率、看有没有 0 行 | 空表上线，仪表盘全空 |
| 对账 | 总数 = 分组和；KPI 人数 = 明细行数；与上期比波动可解释 | 数字错了没人发现，直到有人拿去汇报 |

对账那一行必须能贴出来跑。示例：

```sql
-- 对账1：分组和 = 总数
-- 对账2：明细 COUNT(1) = KPI 的应办人数
```

## 三、汇总与明细同源

同时交付「KPI 卡片」和「下钻明细」时：

1. 两者**共用同一套 CTE**（人员范围、时间切片、状态判定只写一次）。
2. 明细的行数必须等于 KPI 里那个人数。交付前跑一次，把数字写进注释。
3. 汇总用 `GROUP BY`，明细用 `ROW_NUMBER` 出序号，但过滤条件逐字一致。

为什么：口径一致靠同源生成，不靠事后人眼比对。两套各写一遍，必然有一天对不上。
